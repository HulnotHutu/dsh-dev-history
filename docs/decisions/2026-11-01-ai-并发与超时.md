# 决策记录：AI 叙事生成的接口超时与并发改造

日期 2026-11-01 · 状态 已实施 · 落点提交 `ba638bb`（tools/summarize.py）· 现状文档见 [ai-layer.md](../ai-layer.md#并发模型)

> 背景：summarize.py 把 data/arch-notes.json 的紧凑语料逐段交给 DashScope 兼容模式接口，为 narrative.json 的每个阶段（按月）与每个架构区域各生成一个条目草稿。本文记录该流水线因大语料调用 AI 造成接口超时后的方案设计。

## 需求

原实现为串行逐段调用，HTTP 读超时 240 秒。2026-11-01 迁移到新调用接口与 `qwen3.8-2.4t-a95b`（大参数推理模型，出首 token 时间显著长于原模型）后首次全量生成：单段调用在读取阶段抛 `TimeoutError`，整次运行以异常告终，草稿未落盘；草稿在全部段完成后才一次性写盘，中途任何一段失败即全盘作废。

即便把超时调大，串行的总墙钟时间 = 各段之和（当时 5 个阶段 + 4 个区域共 9 段），一次全量生成要等待极久；串行版重跑在完成前被中止，判定为不可接受。需求归纳为三点：单段慢不拖垮整体、总时长收敛到可接受范围、个别段失败不导致整体失败。

## 解决方案

两层修复，落在同一提交：

1. **单段读超时 240s → 600s**（`DASHSCOPE_TIMEOUT` 环境变量可覆盖），对齐 aihelpmed 守护进程的 `call_timeout` 默认值（10 分钟）——大参数推理模型出首 token 可能超过 5 分钟，240s 必然误杀健康调用。
2. **互不依赖的段任务并发化**：9 段（阶段/区域）读的都是只读输入（提取数据、该段现状文案、风格基准），写的目标互不相交，依赖图是纯粹的扇出/汇聚——用 `ThreadPoolExecutor` 并发提交，默认 4 路（`DASHSCOPE_PARALLEL` 可调），墙钟从「各段之和」降为「约一波次之和」。

三条并发正确性约束与串行版对齐：顺序与完成顺序解耦（任务返回值而非改共享状态，主线程按提交顺序收集、按 `ordered_keys` 与区域顺序重装，草稿段落顺序确定，人工 diff 只见内容差异）；对账单点化（slug 对账与格式化在全部结果汇聚后由 `normalize_draft` 跑一次，并发只发生在调 AI 一步）；失败隔离不变（单段失败回退「保留现状」并出报告行，不污染其他段）。

## 具体操作

`tools/summarize.py`（提交 `ba638bb`）：

- 常量层：`AI_TIMEOUT = int(os.environ.get('DASHSCOPE_TIMEOUT', '600'))`；`PARALLEL = int(os.environ.get('DASHSCOPE_PARALLEL', '4'))`；`urlopen(req, timeout=AI_TIMEOUT)`。
- 把原来内联在主循环里的调用逻辑抽出为两个任务函数 `phase_ai(key, cur, payload, seeded)` 与 `region_ai(cur, payload)`：各自调 AI、剔除清单外 slug，失败时返回现状条目与「保留现状」报告行（新阶段失败则整段不收）。
- 主循环改为四段式：主线程先构造全部段的 payload（语料拼接是确定性 CPU 工作，不进线程）→ `ThreadPoolExecutor(max_workers=PARALLEL)` 提交 → 按提交顺序 `fut.result()` 收集并按 key/name 归位 → 按 `ordered_keys` 与区域顺序重装 `draft['phases']` / `draft['regions']`，报告行依提交顺序落。
- 效果实测：并发版 9/9 段全部成功，`--check` 对账报告通过（3 条 gloss 超 24 字属草稿质量问题，人工改写后全绿，不在本决策范围）。CI 化后（sync.yml 的 AI 步骤）继承同一默认参数。

## 备选与落选原因

- **整文档单次调用**（全部段拼成一个大 prompt）：落选——输出 JSON 大而脆，一处格式错误全盘失败；长输出后半段质量稀释，「每段先判断后事实」的风格宪章在长输出里守不住；失败无隔离。
- **阶段内再切分**：落选——月度语料本身只含几十条决策的紧凑清单，不大；叙事要求一段连贯判断，切开即碎化；调用数翻倍反而放大超时暴露面。
- **asyncio / 多进程**：落选——负载是纯 I/O 等待，GIL 无关紧要，线程池足够；脚本其余部分是同步 urllib，线程保持代码平实，asyncio 需要整体改异步；多进程对网络等待毫无意义。
- **只调大超时不并发**：落选——解决单段 240s 误杀，但总墙钟仍是各段之和（串行重跑即因此被中止）；且段间失败概率随串行长度累积。
- **无界并发（全部段同时打满）**：落选——MaaS 工作区有配额与限流（aihelpmed 配额守护进程的存在即证据），一波次打出全部最长 10 分钟的调用是配额脉冲；4 路已是约一波次收敛，`DASHSCOPE_PARALLEL` 留了拉满的口子。
- **失败自动重试队列**：落选——失败段已有「保留现状」回退且在报告可见；并发行使重跑代价很低，值得为简单性放弃重试逻辑。

## 代价与收益

收益：全量生成的墙钟收敛到约一波次；单段慢调用不再误杀、也不再拖垮整体；草稿段落顺序确定，人工校订 diff 干净；失败隔离与回退语义和串行版完全一致；超时/并发/模型全部环境变量可调，模型到期换血不需要改代码——这套参数随后被 CI 的每日同步直接继承。

代价：脚本从单循环变为「构造 payload → 提交 → 收集 → 重装」四段式，复杂度略升；并发度是配额礼貌值而非性能极限，使用者需要理解 `DASHSCOPE_PARALLEL` 的含义；草稿仍最后一次性写盘，中途崩溃没有部分产物——接受，因为并发行使重跑的代价已经足够低。
